## 1. 测试架构与方法（v1）

```
Git 提交(push main)  ──►  GitLab(仓库 / Webhook / PAT)
                          │  webhook: http://192.168.200.12:30080/api/webhook
                          │  （只订阅 deploy 分支变化）
                          ▼
                     ArgoCD(application-controller / repo-server)
                          │  对比 deploy 分支 + apply
                          ▼
                     ns podinfo / ns webapp（v1 时用的是 ns demo）
```

> v1 测试时清单在 `main`、应用是 `demo` 命名空间的 nginx；当前清单在 `deploy` 分支，应用是 `ns podinfo`（podinfo+redis，:30095）与 `ns webapp`（:30096）。断言方法不变。

断言层次：不只查 ArgoCD 的 `Synced/Healthy`，同时核对集群真实对象（副本数、Pod 镜像、Service 是否存在、HTTP 200），避免"状态面板绿但实际没部署"的误判。

判定原则：
- 正例：变更能落地、时间可量化
- 反例（故障注入）：ArgoCD 必须给出明确错误（ComparisonError / Unknown + message），且不得误删或削减现有工作负载

## 3. 关键场景细节

### 3.1 正常发布链路
- Webhook 触发同步稳定在 **3 秒** 量级（GitLab delivery → ArgoCD refresh → apply），远好于默认 3 分钟轮询。
- 镜像变更走滚动更新，2 副本的 Deployment 在更新期间业务端口始终 200，没有出现中断窗口。
- 连续 5 次提交没有产生"中间态卡死"，最终收敛到最后一次 commit，且同代 Pod 镜像一致（校验了滚动更新是否留下混代副本）。

### 3.2 prune 与配置自洽
- `prune: true` 生效，删除 Service 后集群对象被真正回收。
- **反例更有价值**：如果只 `git rm service.yaml` 而不同时改 `kustomization.yaml`，kustomize build 直接失败，ArgoCD 报 ComparisonError 并保持线上资源原样。这是"保护性失败"——错误的提交不会造成半套资源。

### 3.3 故障注入
- 错误镜像 tag：新 ReplicaSet 的 Pod 卡在 ImagePullBackOff，旧 ReplicaSet 的 2 个 Pod 继续服务（HTTP 200），ArgoCD health=Progressing，能体现"更新未完成"。
- requests > limits：K8s 准入直接拒绝该 Deployment，ArgoCD 侧表现为持续重试并记录明确原因，不会把错误配置硬推到集群。
- 非法 YAML / 分支丢失 / 凭据错误：三种都落到 ComparisonError 或 Unknown，message 可定位到具体原因（kustomize build、unable to resolve、authentication required）。

### 3.4 时序数据（可直接用于 SLA 与告警阈值设计）

| 指标 | 实测值 |
|---|---|
| Webhook → 部署完成 | 3s（多次复测 3–4s） |
| 无 Webhook 轮询兜底 | 222s（默认 180s 周期 + 调度耗时） |
| selfHeal 收敛 | 3s |
| GitLab 停机 → 检测到 Unknown | ≤20s（主动刷新后） |
| GitLab 停机 → 服务恢复（HTTP 302 + puma run） | 约 1–2 分钟 |
| GitLab 恢复 → ArgoCD 回到 Synced | ≤20s |

## 4. 生产环境必须知道的行为特征

**① 凭据失效不会立即暴露**

改错密码或撤销 PAT 后，ArgoCD 仍可能长时间显示 Synced。原因是 repo-server 有本地 git 缓存、ArgoCD 有 manifests 缓存，hard refresh 只重算清单、不强制重新 clone。必须"清缓存（重启 repo-server）+ 触发刷新"才会报鉴权失败。

生产影响：token 过期当天可能一切正常，直到下一次真正 fetch 才炸。建议 token 轮换后主动做一次冷验证，或对 `argocd_repo_server` 的 auth 错误配告警。

**② Webhook 只是加速，不是必需**

关掉 webhook 后同步依旧发生，只是从 3s 变成 222s。生产上要监控的是"webhook delivery 失败率"，而不是依赖它保证一致性；同时把轮询周期（`timeout.reconciliation`）设为业务能接受的上限。

**③ prune 与清单自洽强绑定**

删文件必须同时删 kustomization 引用，否则 ArgoCD 报错不动线上资源。这不是 bug，但如果团队只看"有没有报红"而不看 message，容易误判成"同步坏了"。

**④ selfHeal 会覆盖人工操作**

手工 `kubectl scale` 后 3s 被回滚到 Git 声明值。运维排障期间临时改副本会被打回，需要时先关 automated 或打 `argocd.argoproj.io/sync-options: Prune=false` 类豁免。

**⑤ 删除 Application 的两个坑**

- REST DELETE 必须带 `Content-Type: application/json`，否则返回 415；
- 级联删除要 `cascade=true`，且 ArgoCD 默认不删 Namespace（符合预期，但清理脚本别假设 ns 会一起消失）。

## 5. 改进建议（按优先级）

1. **收紧 default AppProject**：当前 `sourceRepos: ["*"]`、destinations 未限制。生产应按项目拆 AppProject，仓库与命名空间白名单化——TC-16 已证明限制生效后的报错信息清晰。
2. **PAT 轮换制度化**：现有 PAT 有效期 330 天，建议 90 天轮换 + 轮换后跑一次冷验证（见特征①）。
3. **补 webhook 失败告警**：GitLab 侧 delivery 失败 + ArgoCD 侧 repo 认证错误，两条告警比"看板绿不绿"可靠。
4. **加部署验收探针**：错误镜像场景下旧副本仍服务，光看 Pod Running 会漏判；建议在 CI 里对 NodePort 做一次 HTTP 断言，或在 ArgoCD 配 resource health 自定义检查。
5. **容量**：当前节点 16 GiB 已用约 12 GiB（可用 2.7 GiB），根盘 72%。v1 测试时只跑 GitLab+ArgoCD（7 GB 内存规划），现在还跑 Keycloak/Sonar/Harbor/Jenkins/Artifactory，余量更小，任何新增组件前都要先扩内存或加节点。
6. **测试环境隔离**：本次用 `demo` 命名空间做故障注入，生产应单独准备演练空间（如 `demo-drill`），避免污染业务。

## 7. 复跑方式

前置：服务器已装 kubectl、curl、jq、git；本机有 `scripts/tools/ssh_exec.py`。

```bash
# 1) 上传测试库与用例脚本
python scripts\tools\ssh_exec.py --put "scripts\pipeline\lib-test.sh=>/root/cicd-test/lib-test.sh" ^
  --put "scripts\pipeline\40-stage-a.sh=>/root/cicd-test/40-stage-a.sh"

# 2) 执行（单阶段，输出直接回显 PASS/FAIL）
python scripts\tools\ssh_exec.py --script scripts\pipeline\40-stage-a.sh --timeout 290
```

一键全量（约 15–20 分钟，会真实改动 demo 应用与 GitLab 仓库，仅限演练环境）：

```bash
python scripts\tools\ssh_exec.py --script scripts\pipeline\run-all.sh --timeout 300   # 分段执行，逐段回显
```

注意：所有用例都会在结束时把仓库 reset 回基线 commit，并恢复 webhook、PAT、syncPolicy、AppProject 白名单。若中途中断，先执行 `scripts/pipeline/99-restore.sh` 复位现场。
