## 1. 一条告警的完整链路（每一跳都在干什么）

```
指标采集                   规则判定                     路由/抑制                格式转换              群消息
────────                 ─────────                   ─────────              ─────────            ──────────
node-exporter 9100 ┐
kube-state-metrics 8080 ├→ Prometheus 每 30s 抓一次 ┐
grafana 3000        │                              ├→ 规则每 30s 评估 ──→ Alertmanager ──→ dingtalk-bridge ──→ 钉钉群机器人
keycloak-metrics 9000 │                              │   (18 条规则)      (分组/抑制/重复)     (渲染 markdown)     (Webhook)
blackbox 9115 ┘                                    │                       9093                8080
                                                 └ 抓不到就是你自己的 up{job=...} 掉线，也会单独告警（TargetDown）
```

四个关键点，理解了就不会配错：

1. **Prometheus 只负责"算"，不负责"发"**：规则产出 `ALERTS` 状态，推给 Alertmanager；Prometheus 自己不发消息。
2. **Alertmanager 只认 webhook 的结构，不认钉钉的结构**：AM 的 payload 是 `{"status":"firing","alerts":[{labels,annotations,...}]}`，钉钉要 `{"msgtype":"markdown","markdown":{"title","text"}}`。所以中间必须有 `dingtalk-bridge` 做转换 —— 这就是为什么不能把 AM 的 receiver 直接指向 `oapi.dingtalk.com`。
3. **分组/抑制在 AM 做，不在规则里做**：`group_by` 决定"同一批告警合成一条消息"，`inhibit_rules` 决定"根因告警压住衍生告警"。规则里只写"什么情况算异常"。
4. **bridge 必须回 2xx 才算送达**：钉钉返回 `errcode=0` 时 bridge 回 200；返回非 0（加签错、关键词不匹配、限流）时 bridge 回 500，AM 会按 `repeat_interval` 重试 —— 这样配错不会被静默吞掉。

## 3. 路由与抑制（`40-alertmanager.yaml`）

```yaml
route:
  receiver: dingtalk-ops            # 默认全部进钉钉
  group_by: [alertname, namespace, instance]
  group_wait: 30s                   # 30s 内的同组告警合并成一条
  group_interval: 2m
  repeat_interval: 4h               # 没恢复的告警 4 小时提醒一次
  routes:
    - matchers: ['severity="critical"']   # critical 单独节奏：10s 就发，30 分钟复报
      receiver: dingtalk-ops
      group_wait: 10s
      repeat_interval: 30m
```

抑制关系（4 组）：

| 根因 | 被压住的 | 为什么 |
| --- | --- | --- |
| `TargetDown` | 同 `instance` 的所有告警 | 一个抓取目标挂了会连锁炸出一堆派生告警 |
| `NodeExporterDown` / `TargetDown` | `NodeDisk*` / `NodeMemoryUsageHigh` / `NodeLoadHigh` | 指标断流时容量数字必然失真 |
| `EntryProbeFailed` | `TLSCert*` | 同一次握手失败的伴生现象 |
| `PodNotReady` | 同 ns/pod 的 `PodCrashLooping` | 同一个 Pod 不重复轰炸 |

## 4. 接入钉钉群：4 步（拿到 Webhook 后 1 分钟完成）

### 第 1 步：在钉钉群里建自定义机器人

群设置 → 机器人 → 添加「自定义」→ 安全设置三选一：

| 模式 | 需要什么 | 推荐度 |
| --- | --- | --- |
| **加签**（推荐） | `SEC` 开头的一串密钥 | 最安全，机器人地址可泄露但无法被乱用 |
| 自定义关键词 | 一个词，比如 `告警`（消息里必须出现） | 简单，但任何知道地址的人都能发 |
| IP 白名单 | 出口 IP | 本环境是 NAT 后单出口，可用但易变 |

### 第 2 步：写进 Secret（**唯一需要改的地方**）

```bash
kubectl -n monitoring create secret generic dingtalk-bot \
  --from-literal=webhook-url='https://oapi.dingtalk.com/robot/send?access_token=xxxxxxxx' \
  --from-literal=secret='SECxxxxxxxx' \
  --from-literal=keyword='' \
  --dry-run=client -o yaml | kubectl apply -f -
```

- 用**加签**模式：填 `secret`，`keyword` 留空；
- 用**关键词**模式：`secret` 留空，`keyword` 填群里设置的词（bridge 会自动把它加到消息末尾）。

### 第 3 步：让 bridge 重新读 Secret

```bash
kubectl -n monitoring rollout restart deploy/dingtalk-bridge
kubectl -n monitoring exec deploy/dingtalk-bridge -- \
  python -c 'import urllib.request;print(urllib.request.urlopen("http://localhost:8080/healthz").read())'
# 期望：{"ok": true, "webhook": true, "sign": true}
```

**env 只在容器启动时读一次**，改 Secret 不重启 = 不生效，这是最容易忘的一步。

### 第 4 步：验收（两级）

```bash
# 4.1 只测 钉钉 ← bridge（跳过 Prometheus/AM）
bash scripts/monitoring/602-dingtalk-test.sh

# 4.2 测全链路：amtool 往 AM 注入一条告警，3 分钟后自动恢复
kubectl -n monitoring exec deploy/alertmanager -- \
  amtool --alertmanager.url=http://localhost:9093 \
  alert add alertname=AlertPipelineTest severity=warning namespace=monitoring \
  instance=amtool-selftest summary="告警链路联调（可忽略）" --duration=3m
```

群里应先后收到两条消息：`⚠️ 告警触发` 与 `✅ 告警已恢复`，末尾带 Grafana / Prometheus 链接。

两个容易误判的点：

- `amtool alert add` 的 `--duration` 参数在本版本（AM 0.27）**不存在**，别照抄网上写法；要么直接 `alert resolve`，要么用 `--end`。
- `amtool` 的 `description=` 值含空格/中文会被 matchers 解析器警告（只是 warn，告警仍会创建）；想干净就加引号 `description="..."`。

### 改规则的三个坑（本轮全踩了一遍）

1. **CM 改完，Pod 里的文件不会立刻变**：`kubectl replace cm` 后要等 kubelet 同步（实测 40–60s）。抢在前面 `POST /-/reload` 会**成功但仍是旧规则**（返回 200、规则数没变），很容易以为"改了没用"。
   正确顺序：改 CM → 等 45s → `kubectl -n monitoring exec deploy/prometheus -- grep -c <新规则名> /etc/prometheus/rules/corp-rules.yml` 确认到 1 → 再 reload。
2. **缩进错了 reload 直接 500**：CM 里 `data.corp-rules.yml` 是**已去掉块缩进后的内容**，`groups` 顶格、组项 2 空格、`rules` 4 空格、`- alert` 6 空格。按清单文件的缩进往 CM 里追加会变成"上一组的 rule"，报 `field name not found in type rulefmt.RuleNode`。
3. **改完先跑 promtool**：`kubectl -n monitoring exec deploy/prometheus -- promtool check rules /etc/prometheus/rules/corp-rules.yml`，比看 reload 返回码快得多。热加载用 `curl -X POST http://prometheus.monitoring.svc.cluster.local:9090/-/reload`（Pod 内执行；宿主打 ClusterIP 会 000）。

## 5. 钉钉加签到底怎么算（bridge 已实现，了解即可排错）

钉钉要求把 `timestamp`（毫秒）和 `sign` 拼到 webhook 地址上：

```
to_sign  = timestamp + "\n" + secret
sign     = urlencode(base64(HmacSHA256(to_sign, key = secret)))
final    = webhook_url + "&timestamp=" + ts + "&sign=" + sign
```

三个高频错误：

| errcode | 消息 | 原因 |
| --- | --- | --- |
| `310000` | `sign not match` | `secret` 填错、或用了关键词模式却填了 secret、或服务器时间偏差 > 1 小时（容器时间要准） |
| `310000` | `keywords not in content` | 关键词模式但消息里没有该词（bridge 已自动附加） |
| `310000` | **`ip 不在白名单中`** | 机器人安全设置选了 **IP 白名单**，但节点出口公网 IP 不在名单里。**本环境实测出口是双 IP**（`120.195.66.106` / `117.62.151.91`，不同目标走不同出口），白名单随时可能命中不了 —— **不要用 IP 白名单，改加签或关键词** |
| `130101` | `send too fast` | 超过 20 条/分钟（bridge 有软限流，会丢并打印日志） |

## 6. 排障速查

| 症状 | 先看什么 | 结论方向 |
| --- | --- | --- |
| 群里没消息，AM 显示 `Failed to send` | `kubectl -n monitoring logs deploy/dingtalk-bridge --tail=30` | 有 `resp: {"errcode":...}` 就是钉钉侧拒收（见上表）；有 `webhook 未配置` 就是第 2 步没做 |
| AM 里没有这条告警 | `curl /api/v1/rules` 看规则是否加载；`/api/v1/alerts` 看是否 INACTIVE | 规则没挂上（CM 路径不对）或表达式不成立 |
| 规则加载了但从不触发 | 直接在 Prometheus 里跑表达式 | 表达式返回空 = 阈值/标签不匹配（`fstype`、`mountpoint` 最容易错） |
| 告警一直重复 | 看 `repeat_interval`；看 `group_by` 是否把不同实例拆开了 | 误把 `instance` 放 group_by 会一条实例一条消息 |
| 消息里中文乱码/截断 | 钉钉 markdown 单条上限约 20000 字节；`max_alerts: 10` | 超长时 AM 只发前 10 条，bridge 追加"其余省略" |
