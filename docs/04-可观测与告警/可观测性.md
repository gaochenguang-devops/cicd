## 5. 告警通道：为什么必须有一个 bridge

钉钉群机器人（以及企业微信群机器人）要求载荷是：

```json
{"msgtype":"markdown","markdown":{"content":"..."}}
```

而 Alertmanager 原生 webhook 发的是 `{status, alerts:[{labels, annotations, startsAt…}]}` —— **两者不兼容**，硬把 AM 的 URL 指向群机器人只会报 `400 invalid param`。

所以链路是：`Prometheus → Alertmanager → dingtalk-bridge(转换 + 加签) → 钉钉机器人`。
**现状：钉钉已通**（机器人安全设置=加签，Secret `monitoring/dingtalk-bot` 存 `webhook-url` 与 `secret`），触发与恢复各 2 次实测 `{"errcode":0}`；企业微信/邮件保留定义但不参与路由。

### 5.1 接钉钉（现状，4 步）

```bash
# 1) 钉钉群里加自定义机器人，安全设置选「加签」，复制 Webhook 与 SEC 开头的密钥
#    ⚠️ 不要选「IP 地址段」：本机是双公网出口（120.195.66.106 / 117.62.151.91），白名单必然漏一边

# 2) 写入 Secret
kubectl -n monitoring create secret generic dingtalk-bot \
  --from-literal=webhook-url='https://oapi.dingtalk.com/robot/send?access_token=<TOKEN>' \
  --from-literal=secret='SEC<KEY>' --dry-run=client -o yaml | kubectl apply -f -

# 3) 让 bridge 重新读环境变量
kubectl -n monitoring rollout restart deploy/dingtalk-bridge
kubectl -n monitoring rollout status deploy/dingtalk-bridge
kubectl -n monitoring exec deploy/dingtalk-bridge -- wget -qO- http://localhost:8080/healthz
# 期望 {"ok":true,"webhook":true,"sign":true}

# 4) 自测（amtool 造一条假告警，AM 会走真实路由）
kubectl -n monitoring exec deploy/alertmanager -- amtool --alertmanager.url=http://localhost:9093 \
  alert add alertname="DingtalkSmokeTest" severity=critical instance="smoke" \
  alertname="DingtalkSmokeTest"
kubectl -n monitoring logs deploy/dingtalk-bridge --tail=5
```

bridge 关键行为（改它之前先看）：`HMAC-SHA256(secret, timestamp+"\n"+secret)` → base64 → urlencode 拼 `timestamp`/`sign`；钉钉返回 `errcode!=0` 时向 AM 回 500 让重试；软限流 20 条/分钟；`send_resolved: true` 所以恢复也会推。加签算法与 errcode 对照表见 `docs/04-可观测与告警/告警接入.md`。

### 5.2 企业微信（备用通道，未路由）

bridge 与 Secret 名都保留，只是 `40-alertmanager.yaml` 里没有路由到 `wechat-ops`。要用时把默认 receiver 换回 `wechat-ops` 并补 key：

```bash
kubectl -n monitoring create secret generic wechat-webhook \
  --from-literal=WECHAT_WEBHOOK_URL='https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<你的KEY>' \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n monitoring rollout restart deploy/wechat-bridge
```

### 5.3 邮件（备用通道，未路由）

`40-alertmanager.yaml` 的 `global` 段填 `smtp_smarthost / smtp_from / smtp_auth_*`，并把 `email-ops` 的 `to` 填上。更干净的做法是口令放 Secret + `smtp_auth_password_file`。

### 5.4 路由策略（现状）

```
route: receiver=dingtalk-ops, group_by=[alertname, namespace, instance],
         group_wait=30s, group_interval=2m, repeat_interval=4h
├─ severity=critical → dingtalk-ops（group_wait 10s，repeat 30m）
inhibit（4 组）：
  TargetDown            → 同 instance 的容量/衍生告警
  NodeExporterDown      → 容量类
  EntryProbeFailed      → TLSCertExpiring*
  PodNotReady           → 同 ns/pod 的 PodCrashLooping
```

含义：**所有告警都进同一个钉钉群**，critical 来得更快（10s 起报、30 分钟重复）；抑制规则只压衍生噪音，不压根因。`wechat-ops` / `email-ops` 在 receivers 里有定义，路由里没有。

## 7. 踩坑记录（三个都实际踩了）

### 7.1 hostPath + 滚动更新 = Prometheus 起不来（TSDB 锁冲突）

- 现象：更新 Prometheus 后新 Pod `CrashLoopBackOff`，日志 `opening storage failed: lock DB directory: resource temporarily unavailable`；
- 原因：Deployment 默认 RollingUpdate，新旧 Pod 同时挂同一个 hostPath，TSDB 是单写者；
- 修法：`strategy: type: Recreate`（Prometheus 与 Alertmanager 都已改）。**这是单节点 + hostPath 的通用结论**，以后任何单写者存储都照此办；
- 反过来也提醒：改 Deployment 后若看到"新 Pod 起不来、旧 Pod 还在"，先查锁/端口占用，不要怀疑镜像。

### 7.2 规则文件路径必须靠 `items` 显式落子目录

ConfigMap 的键默认平铺成 `/etc/prometheus/<key>`，而 `prometheus.yml` 里写的是 `/etc/prometheus/rules/*.yml`。不给 `items` 映射，规则就"加载成功但 0 组"（`/api/v1/rules` 返回空数组，极易误判为语法错误）。

2026-11-27 起规则已从 `prometheus-config` 拆成独立 CM，挂载写法是：

```yaml
volumes:
  - name: config
    configMap:
      name: prometheus-config
      items:
        - {key: prometheus.yml, path: prometheus.yml}
  - name: rules
    configMap:
      name: prometheus-rules
      items:
        - {key: corp-rules.yml, path: corp-rules.yml}
# 容器内：mountPath /etc/prometheus/rules
```

改规则的三个坑（CM 同步延迟 40–60s、缩进必须按去块缩进后写、改前先 `promtool check rules`）见 `docs/04-可观测与告警/告警接入.md`。

### 7.3 从宿主 `curl` 打不通 ClusterIP

`curl http://argocd-metrics.argocd.svc.cluster.local:8082/metrics` 在宿主上返回 `000`，但在 Pod 里 200。宿主不在 Service 网段，验证 ClusterIP 端点一律 `kubectl exec` 进 Pod 做，别用宿主 curl 得到"服务挂了"的错误结论。

### 7.4 部署顺序会拖累网关（已修，但要知道原理）

首次部署时 `monitoring` ns 尚不存在，而网关 `nginx.conf` 里已写了 `prometheus.monitoring.svc.cluster.local:9090` 静态 upstream → 网关启动即 `[emerg] host not found in upstream`，两副本各重启 5 次。改成 `resolver` + 域名后，本环境 DNS 被主机侧代理劫持，nginx 拿到 `198.18.0.x` 伪地址，jenkins/argocd/podinfo/alertmanager 直接 502。最终改为 `set $backend <ClusterIP>:<port>`（不查 DNS）才彻底稳定，详见 `docs/01-入口与网络/访问层与证书.md` 5.6。

**这是"新增组件 + 改网关"这类变更的通用教训**：先建后端、再改网关路由；网关侧不要依赖 DNS 解析。

### 11.2 看板怎么进来的（不用手动点 Import）

官方 JSON 下载端点：`https://grafana.com/api/dashboards/<id>/revisions/latest/download`。

规范化两件事，否则面板全空：

1. 删掉 `__inputs` / `__requires`（那是 Import 向导用的，providing 走文件不需要）；
2. 把 `datasource` 里的 `${DS_PROMETHEUS}` / `${VAR_DATASOURCE}` 全部换成数据源 uid **`prom-main`**（连 panel 内的 `datasource.uid` 一起归一）。

结果文件放 `/root/grafana-dash/normalized/`，再整体挂进 `/var/lib/grafana/dashboards`。

### 11.3 踩到的坑：53 万字节的 ConfigMap 建不出来

`kubectl create cm grafana-dashboards --from-file=...` 后被 API 拒绝：

```
The ConfigMap "grafana-dashboards" is invalid: metadata.annotations: Too long: may not be more than 262144 bytes
```

原因：`kubectl create` 会把整份对象写进 `kubectl.kubernetes.io/last-applied-configuration` 注解，而 4 张看板合计 531KB，注解直接超了 256KB 上限。`kubectl apply` 走的也是同一条路。

**正确写法**（不写该注解，直接建对象）：

```bash
kubectl -n monitoring delete cm grafana-dashboards --ignore-not-found
kubectl -n monitoring create cm grafana-dashboards --from-file=/root/grafana-dash/normalized --save-config=false
```

`--save-config=false` 是关键。代价是这份 CM 之后不能 `apply` 更新，要改就删了重建（看板变更频率极低，可接受）。

另一个连锁现象：CM 不存在时 Grafana Pod 一直 `ContainerCreating`，事件里是
`MountVolume.SetUp failed for volume "dashboards": configmap "grafana-dashboards" not found`——
**不要把 ContainerCreating 当成镜像拉不下来**，先看 `kubectl describe pod` 的 Events。

### 11.6 为什么"监控所有服务"靠 blackbox 兜底

Harbor / Jenkins / SonarQube(社区版) / JFrog OSS **都没有可用的原生 Prometheus 端点**（`/metrics` 404 / 不存在）。在没装 exporter 的前提下，"服务是否活着、证书是否过期、入口是否 5xx"这三件事只能由 blackbox 的 `probe_success`、`probe_ssl_earliest_cert_expiry`、`probe_http_status_code` 回答；业务内部指标（队列、构建时长、扫描通过率）要等 CI 指标那一步（§10 第 1 项）。

看板与指标的对应关系，避免"打开看板一片灰以为坏了"：

| 看板 | 依赖 | 现状 |
| --- | --- | --- |
| 15757 / 1860 / 13332 | ksm / node-exporter | 有数据 |
| 13659 | `blackbox-http` job | 有数据（13 target） |
| CI 相关（Jenkins/Sonar） | 需先装插件/exporter | **暂无，属 §10 计划** |
