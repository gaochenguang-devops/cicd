# 企业微信告警接入教程（照着敲版）

目标：让 Alertmanager 的 **critical 告警同时进企业微信群和钉钉群**，warning 仍只进钉钉。全程复用集群里已经在跑的 `wechat-bridge`，不新建服务、不改镜像。

**本教程基于 2026-11-27 现场实测**，开始前先看这张前提表——这四件事已经确认过，你不用再查：

| 前置项 | 实测结果 |
| --- | --- |
| 服务器出网到企业微信 | `https://qyapi.weixin.qq.com/cgi-bin/gettoken` 返回 **200**，耗时 0.17 s |
| 宿主机 Python | `python3 3.12.16`（`/usr/bin/python3`） |
| 桥服务 | `ns monitoring` 的 `wechat-bridge` 1/1 Running，ClusterIP `10.101.25.208:8080` |
| 桥的代码 | `ConfigMap wechat-bridge-src` 里的 `bridge.py`，已支持企业微信群机器人（读 `WECHAT_WEBHOOK_URL`） |
| 当前缺口 | Secret `monitoring/wechat-webhook` **不存在**；Alertmanager 里有 `wechat-ops` receiver 但**没有路由** |

所以真正要做的只有三件事：**建机器人 → 填 Secret 并重启桥 → 给 Alertmanager 加一条路由**。

---

## 第 0 步：开工前 30 秒体检

在 Windows 仓库目录执行（以下所有 `ssh_exec.py` 命令都在这里跑）：

```powershell
cd C:\Users\morning\Desktop\cicd
python scripts\tools\ssh_exec.py "kubectl -n monitoring get pods -l app=wechat-bridge; curl -sS -o /dev/null -w 'qyapi:%{http_code}\n' --max-time 8 https://qyapi.weixin.qq.com/cgi-bin/gettoken"
```

期望看到：`wechat-bridge-xxxx 1/1 Running` + `qyapi:200`。

任何一项不对就先停下：桥没起来看 `kubectl -n monitoring logs deploy/wechat-bridge`；`qyapi` 不通说明这台机器出网被限，本教程走不通，需要先解决代理。

---

## 第 1 步：在企业微信里建群机器人（约 2 分钟）

1. 打开企业微信，进入**要收告警的群**（建议新建一个「CI/CD 告警」群，别用闲聊群）。
2. 群右上角「…」→ **群机器人** → **添加**。
3. 名称填 `CI/CD 告警`，点击添加。
4. 复制弹出的 **Webhook 地址**，形如：
   `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=693a91f6-7xxx-4bc4-97a0-0ec2sifa5aaa`
5. 先别关页面——下一步要用这个 key。

> 安全提醒：这个 key 等于「往这个群发消息的权限」，**不要发到聊天、不要提交到 Git**。泄露了就在群机器人里删掉它重建。

---

## 第 2 步：把 key 写进 K8s Secret（1 条命令）

把 `<把key粘贴到这里>` 换成第 1 步复制的那串 key（**只要 key，不要整条 URL**）。

```bash
export WECOM_KEY='<把key粘贴到这里>'

kubectl -n monitoring create secret generic wechat-webhook \
  --from-literal=WECHAT_WEBHOOK_URL="https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=${WECOM_KEY}" \
  --dry-run=client -o yaml | kubectl apply -f -
```

校验（只确认键在，不打印明文）：

```bash
kubectl -n monitoring get secret wechat-webhook -o go-template='{{range $k,$v := .data}}{{$k}}{{"\n"}}{{end}}'
```

期望输出一行 `WECHAT_WEBHOOK_URL`。Secret 已存在时上面命令会自动覆盖，不用先删。

---

## 第 3 步：重启桥 + 直连自测（这一步过了，链路就通了一半）

**Secret 是 Pod 启动时读进环境变量的，必须重启才生效**，这是最容易漏的一步。

```bash
kubectl -n monitoring rollout restart deploy/wechat-bridge
kubectl -n monitoring rollout status deploy/wechat-bridge --timeout=120s
```

造一个「假告警」直接打给桥（模拟 Alertmanager 的请求体）：

```bash
cat >/tmp/test-alert.json <<'EOF'
{"version":"4","status":"firing","alerts":[{"status":"firing",
 "labels":{"alertname":"WecomSelfTest","severity":"warning","instance":"gateway.corp.local"},
 "annotations":{"description":"企业微信桥自测，收到即通"},
 "startsAt":"2026-11-27T06:00:00Z","endsAt":"0001-01-01T00:00:00Z","fingerprint":"selftest001"}]}
EOF

curl -sS -X POST http://10.101.25.208:8080/webhook \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/test-alert.json \
  -w '\nHTTP:%{http_code}\n'
```

**判断标准**：

- 返回 `HTTP:200`，并且企业微信群里出现「【告警触发】共 1 条 / 告警: WecomSelfTest …」→ **通了，进第 4 步**。
- 返回 `HTTP:500` → 看桥日志：`kubectl -n monitoring logs deploy/wechat-bridge --tail=30`，多半是 key 错或没配。
- 返回 200 但群里没消息 → 桥只认 HTTP 状态、不校验 errcode，直接手动测机器人：

```bash
curl -sS "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=${WECOM_KEY}" \
  -H 'Content-Type: application/json' \
  -d '{"msgtype":"text","text":{"content":"机器人直连测试"}}'
```

返回 `{"errcode":0,"errmsg":"ok"}` 说明机器人和网络都正常，问题在桥（回去看第 2 步 Secret、第 3 步有没有重启）。
返回 `93000` = key 无效/机器人已被删；返回 `45009` = 触发了 20 条/分钟的限流，等一分钟再试。

## 第 4 步：给 Alertmanager 加路由（改一处 YAML）

### 4.1 先备份

```bash
kubectl -n monitoring get cm alertmanager-config -o yaml > /root/am-backup-$(date +%F-%H%M).yaml
ls -l /root/am-backup-*.yaml
```

> 备份文件里含 SMTP 占位，不含真实口令，可以留着。

### 4.2 编辑

```bash
kubectl -n monitoring edit cm alertmanager-config
```

在 `route:` 下的 `routes:` **最前面**插入这三段（缩进对齐现有的 `- matchers:`，4 个空格起头）：

```yaml
  routes:
    # ↓↓↓ 新增：critical 双通道，企业微信 + 钉钉都发
    - matchers: ['severity="critical"']
      receiver: wechat-ops
      group_wait: 10s
      repeat_interval: 30m
      continue: true
    # ↑↑↑ 新增结束，下面保留原来的 critical → dingtalk-ops 路由
    - matchers: ['severity="critical"']
      receiver: dingtalk-ops
      group_wait: 10s
      repeat_interval: 30m
```

`continue: true` 是关键：不加它，Alertmanager 命中第一条路由就停，钉钉就收不到了。

`receivers:` 里已有的 `wechat-ops` **不用动**（就指向 `http://wechat-bridge.monitoring.svc.cluster.local:8080/webhook`）。

保存退出（vim：`Esc` → `:wq`）。

### 4.3 等同步 + 热加载

ConfigMap 改完 kubelet 要 40–60 s 才刷进 Pod，**不要立刻 reload**：

```bash
sleep 60
curl -sS -X POST http://10.103.87.112:9093/-/reload -w '\nHTTP:%{http_code}\n'
```

- `HTTP:200` → 配置生效。
- `HTTP:400` → YAML 写错（缩进/引号），配置**没有生效、旧配置继续跑**，去 `kubectl -n monitoring logs deploy/alertmanager --tail=20` 看报错行，改完重来。

---

## 第 5 步：端到端验证（触发 + 恢复各一条）

### 5.1 触发

```bash
curl -sS -X POST http://10.103.87.112:9093/api/v2/alerts \
  -H 'Content-Type: application/json' \
  -d '[{"labels":{"alertname":"WecomE2E","severity":"critical","instance":"gateway.corp.local"},
       "annotations":{"description":"端到端验证：企业微信 + 钉钉"},
       "startsAt":"2026-11-27T06:10:00Z","endsAt":"0001-01-01T00:00:00Z"}]' \
  -w '\nHTTP:%{http_code}\n'
```

等 10–20 s（路由 `group_wait: 10s`），**两个群都应该收到**。

### 5.2 恢复

```bash
END=$(date -u -d '-1 minute' +%Y-%m-%dT%H:%M:%SZ)
cat >/tmp/resolve.json <<EOF
[{"labels":{"alertname":"WecomE2E","severity":"critical","instance":"gateway.corp.local"},
 "annotations":{"description":"端到端验证：企业微信 + 钉钉"},"endsAt":"$END"}]
EOF

curl -sS -X POST http://10.103.87.112:9093/api/v2/alerts \
  -H 'Content-Type: application/json' --data-binary @/tmp/resolve.json \
  -w '\nHTTP:%{http_code}\n'
```

两个群应收到「【告警恢复】」。恢复消息靠 `send_resolved: true`（receiver 里已开）和**完全一致的 labels**，少一个 label 就匹配不上、只会有新告警。

## 第 6 步：定稿策略（可选，但建议）

| 告警 | 钉钉 | 企业微信 | 理由 |
| --- | --- | --- | --- |
| critical | ✅ | ✅ | 值班群和业务群双保险，谁先看到谁处理 |
| warning / info | ✅ | ❌ | 量大会触发机器人 20 条/分钟限流，把重要消息挤掉 |
| 恢复（resolved） | ✅ | ✅ | 双通道都要闭环，避免「以为还挂着」 |

想让 warning 也进微信，把第 4 步路由的 matcher 改成 `severity=~"critical|warning"`，然后重新走 4.3；但先确认自己的告警量，超过 20 条/分钟就得先做聚合。

---

## 第 7 步：排障速查（按现象查）

| 现象 | 最可能的原因 | 处理 |
| --- | --- | --- |
| 群里完全没消息，桥日志无报错 | Secret 建了但没重启 Pod | `rollout restart deploy/wechat-bridge`，再跑第 3 步 |
| 直连桥返回 500 | key 写错 / Secret 键名不是 `WECHAT_WEBHOOK_URL` | 核对 Secret 键名与第 2 步命令 |
| 机器人直连返回 93000 | key 无效、机器人被移除、key 抄漏字符 | 重新复制 Webhook 地址 |
| 机器人直连返回 45009 | 超过 20 条/分钟 | 等 1 分钟；长期靠聚合/降级 warning |
| 桥返回 200，群里有消息但内容截断 | 单条 markdown 超 4096 字节 | 当前模板最多 10 条告警，告警风暴时正常现象，靠分组收敛 |
| Alertmanager 改了 CM 没反应 | 没等 kubelet 同步 / 没 reload | `sleep 60` 后再 `POST /-/reload` |
| reload 返回 400 | YAML 缩进、引号、`continue` 拼错 | 看 alertmanager 日志定位行号，改完重来 |
| 只收到钉钉、收不到微信 | 路由没加 `continue: true` 或被前面的路由截胡 | 把微信路由放到 `routes:` 最前 |
| 恢复消息不来 | labels 与触发时不一致 / `send_resolved` 关闭 | 用完全相同的 labels；确认 receiver 里 `send_resolved: true` |
| 中文乱码 | Windows 端 curl 编码问题（服务器端正常） | 用文件 `--data-binary`，不要命令行拼中文 |

---

## 第 8 步：回滚（30 秒）

```bash
# 恢复备份（覆盖 CM）
kubectl -n monitoring apply -f /root/am-backup-*.yaml
sleep 60
curl -sS -X POST http://10.103.87.112:9093/-/reload -w '\nHTTP:%{http_code}\n'
```

只想撤微信通道也行：编辑 CM 删掉第 4 步插入的那 5 行，等 60 s 再 reload。桥和 Secret 留着不影响任何现有告警。

## 第 9 步：进阶（现在不做，知道边界就行）

| 想解决 | 要做什么 | 注意 |
| --- | --- | --- |
| 按值班人定向推送、发应用消息卡片 | 改用企业微信**自建应用**（corpid/secret/agentid）；当前 `bridge.py` 只支持群机器人，要改 CM 里的代码 | 后台必须配「企业可信 IP」= 这台机器的**出口** IP，否则报 60020 |
| 告警风暴刷屏 | 桥加 fingerprint 去重 + 令牌桶限流 | 现在没有去重，同一告警重试会重复发 |
| 桥自身挂了没人知道 | 给桥加 `/healthz`，再用 blackbox 探 | 现在没有健康检查端点，直接探会 404 |
| 微信侧也做升级通知 | Alertmanager 加第二级 receiver + `repeat_interval` 递进 | 需要值班表，单群机器人做不了按人升级 |

改 `bridge.py` 的固定动作：改 ConfigMap → **等 60 s** → `kubectl -n monitoring rollout restart deploy/wechat-bridge`（ConfigMap 变更不会自动重启进程，这一步不做等于没改）。
