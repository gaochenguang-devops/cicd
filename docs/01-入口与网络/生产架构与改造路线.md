# 组件组合的生产化方案（192.168.200.12 现状 → 目标态）

> 写于 2026-11-27。现状口径以 
>
> `README.md`
>
> 「服务全景」为准（15 个平台/业务组件 + 8 个监控组件、单节点 kubeadm、8C/22G、根盘 64G 用 52G（82%））。
> 本文回答一个问题：
>
> **这些组件怎么 "结合" 才像生产**
>
> —— 不是再加一堆新组件，而是把已有的排成一条能问责、能回滚、能审计的链路。

## 0. 一句话判断

现在的平台**单个组件都够看，组合方式还是演示形态**。三个最扎眼的差距：



1. **两条 CI 并存且职责重叠**（GitLab CI 主链路 + Jenkins 独立链路），凭据、门禁、制品路径各一套；

2. **没有入口层**：8 个服务全部 NodePort 直连、全 HTTP、无 TLS、无统一域名 —— 生产环境的 "入口" 这一层是缺的；

3. **数据没有保护**：PV 全是 hostPath、PG 全是单实例、`/data` 六个目录零备份、零恢复演练。

所以生产化的顺序应该是 **入口 → 数据 → CI 收敛 → 可观测 → HA**，而不是反过来先堆高可用。

## 1. 现状分层：哪些已经是 "生产形态"，哪些是 "演示形态"



| 组件                  | 当前组合方式                                            | 判定                     | 缺口                                                 |
| ------------------- | ------------------------------------------------- | ---------------------- | -------------------------------------------------- |
| OpenLDAP + Keycloak | LDAP 唯一账号源 → Keycloak 联邦 + OIDC 发 5 张牌            | **已是生产形态**（架构对，只差 HA）  | Keycloak 单实例；LDAP 单容器 389 明文                       |
| GitLab              | 宿主机 omnibus + `main`/`deploy` 双分支 + webhook       | 生产形态的 "半成品"            | 单机无 HA；deploy 分支靠 `resource_group` 防并发，是 "补丁式" 一致性 |
| GitLab Runner       | **shell executor，直接在宿主机跑 podman**                 | **演示形态**               | 构建污染宿主、无法限制资源、无法复现；`concurrency=1` 是无奈之举           |
| Harbor              | 项目 `apps`/`library` + 两个项目级 robot + manifest 读回校验 | 生产形态                   | 单实例；HTTP；镜像无扫描 / 签名                                |
| SonarQube           | 独立 PG + `cicd-gate` + CI 侧 `qualitygate.wait`     | 生产形态（门禁设计很正）           | 单实例 ES；无趋势报表归档                                     |
| Artifactory OSS     | Generic 仓 + jar/sha256/build-info                 | **演示形态**               | OSS 无权限模型（非 admin 只读）；无保留策略清理                      |
| ArgoCD              | GitOps + `deploy` 分支 + webhook + Dex→Keycloak     | **生产形态**（这是全平台最像生产的一环） | 无 syncWindow / 审批；无 ApplicationSet 分环境             |
| Jenkins             | K8s 内 JCasC + 共享库 + 5 stage                       | 生产形态的 "第二套"            | 与 GitLab CI 重叠；镜像无 daemon 靠 Jib                    |
| podinfo / webapp    | 三探针 + HPA + PDB + NetworkPolicy + 非 root          | **生产形态**（工作负载标准很正）     | 无灰度 / 无金丝雀；资源配额未设                                  |
| 可观测                 | 只有 metrics-server（给 HPA 用）                        | **演示形态**               | 无指标存储、无告警、无日志聚合、无链路追踪                              |
| 暴露方式                | 8 个 NodePort，无 Ingress                            | **演示形态**               | 无域名、无 TLS、无访问控制、无 WAF                              |

结论：**身份、仓库、门禁、部署四件事的 "骨架" 是对的，缺的是入口层、数据保护、CI 收敛和可观测**。

## 2. "结合" 的五条原则（这是本文的核心）

### P1 身份只认一条链：LDAP → Keycloak → OIDC

所有面向人的系统只接 Keycloak，不各自建号；`groups` claim 是唯一授权依据。**Artifactory 是唯一例外**（OSS 不支持 OAuth），生产化要么升级 Pro 接 OIDC，要么把它降级为 "只给 CI 用的机器仓"，人不直接登录。

> 现状已经做到了 5/6，剩下 Artifactory。这条不改，后面所有审计都对不上人。

### P2 三种仓库各自唯一，禁止交叉



| 仓库          | 只存                                     | 谁读          |
| ----------- | -------------------------------------- | ----------- |
| GitLab      | 源码 + 部署清单（`deploy` 分支）                 | 人、CI、ArgoCD |
| Harbor      | 运行镜像                                   | K8s、人（排查）   |
| Artifactory | 交付制品（jar/tar.gz + sha256 + build-info） | 审计、下游构建     |

**镜像不进 Artifactory、制品不进 Harbor、清单不进镜像**—— 现在就是这么做的，这是对的，不要 "顺手" 打破。

### P3 CI 必须收敛成一条（当前最大的结构性问题）

现在两条链路并行，代价很具体：凭据 5+5 套、门禁调用两种写法（`sonar.qualitygate.wait` vs 手动查 API）、制品路径两种规范（`<sha>.tar.gz` vs `1.0.<N>/`）、两套共享库 / 脚本维护。



| 维度          | A：GitLab CI 为主（推荐）                        | B：Jenkins 为主                               |
| ----------- | ----------------------------------------- | ------------------------------------------ |
| 现有成熟度       | 主链路已在跑，podinfo/webapp 都靠它                 | `maven-demo` 刚跑通，未接部署                      |
| 构建隔离        | **差**（shell executor 直接用宿主 podman / 文件系统） | **好**（每次构建在 K8s Pod/PVC 里）                 |
| 多语言 / 复杂流水线 | 一般（YAML 表达力弱）                             | **强**（共享库 + Groovy）                        |
| 维护成本        | 低（GitLab 自带）                              | 中（JCasC / 插件 / 凭据都要自己管）                    |
| 迁移代价        | 小（保住现状，Jenkins 只留 "独立任务"）                 | 大（podinfo/webapp 要重写，ArgoCD 的 deploy 写回要搬） |

**推荐 A**：GitLab CI 做 "发版主链路"（它已经承担 deploy 写回 + ArgoCD 触发），Jenkins 收缩为 "独立 / 遗留 / 一次性任务" 的执行器（比如 maven 老项目、需要 K8s 隔离的构建），并明确一条规矩：**只有一条链路允许写&#x20;**`deploy`**&#x20;分支**。

如果反过来选 B，就必须先把 Runner 从 shell executor 换成 K8s executor，否则 "生产" 名不副实。

### P4 阶段标准化：两条链路共用同一套阶段语义

不管是哪种 CI，阶段固定为 8 段，缺哪段就在该段留空但显式声明：



```
拉代码 → 静态扫描(门禁) → 单测+覆盖率 → 构建 → 镜像扫描(门禁) → 制品+校验+SBOM → 写清单 → ArgoCD 部署(可审批)
```

现状缺口在第 3 段（无覆盖率门禁）和第 5 段（镜像不扫）。这两段补齐后，"能不能上线" 就有三个独立闸门（代码质量 / 单测 / 镜像漏洞），而不是现在的一个。

### P5 环境分层靠 "分支 + 目录 + Application"，不靠多套集群

单节点现实下，最有性价比的分层：



* `main` = 代码，`deploy-staging` / `deploy-prod` 两个清单分支；

* ArgoCD 两个 Application（`-staging` 自动同步、`-prod` 手动 sync 或配 `syncWindow`）；

* 生产 Application 设 `syncPolicy: {}`（不自动），配合 ArgoCD 的 "审批人 + 差异预览" 当发布审批。

这能在不买第二台机器的情况下，把 "改了就上线" 变成 "改了要过闸"。

## 3. 目标态架构（在现有组件上做 "加法"，不换栈）



```
                    ┌──────── 入口层（新增）────────┐
  浏览器/CI ──TLS──► │ Ingress-NGINX（单入口 + 域名 + 证书）│
                    └───────────────┬───────────────┘
                                    │ 全部后端走 ClusterIP（NodePort 只留运维应急）
      ┌──────────────┬──────────────┼───────────────┬──────────────┐
      ▼              ▼              ▼               ▼              ▼
  GitLab        Jenkins        Harbor          Sonar         Artifactory
 (源码+清单)   (独立任务)     (镜像)         (质量门禁)      (制品+审计)
      │              │              ▲               ▲              ▲
      └── CI（唯一一条）─────────────┴───────────────┴──────────────┘
                     │ 写 deploy 分支
                     ▼
                  ArgoCD ──► K8s（podinfo / webapp / maven-demo）
                     ▲
      ┌──────────────┴───────────────┐
      │ 可观测层（新增）              │ 数据层（改造）
      │ Prometheus + Grafana + Alertmanager │ PG 集中/备份 + PV 备份 + etcd 快照
      │ Loki（日志）+ 审计日志          │ Secret 统一（Sealed/KMS）
      └──────────────────────────────┘
```

新增的组件只有四类：**Ingress + 监控告警 + 日志 + 备份**。其余全是改造。

## 4. 改造矩阵（组件 × 动作 × 优先级）

### P0 止血（不做就等于没有生产）



| # | 动作                                                                                                                          | 涉及                                              | 验收                                             |
| - | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| 1 | **备份 + 恢复演练**：etcd 快照、5 个 PG（gitlab/sonar/harbor/artifactory/keycloak）`pg_dump`、`/data` 六目录 rsync、Harbor registry 目录        | 全平台                                             | 在临时目录成功恢复一次 Sonar 库 + 一次 Harbor registry，并记录耗时 |
| 2 | **Ingress + TLS**：装 ingress-nginx，8 个服务收敛到域名（`gitlab.corp.local` 等），证书用内部 CA / 自签                                           | GitLab 例外（宿主 nginx 占 80，需改为反代到 Ingress 或保留独立入口） | 全部 HTTPS、NodePort 只留应急；OIDC 回调地址同步改            |
| 3 | **告警**：Prometheus 抓 `kube-state-metrics` + node-exporter + 各服务 `/metrics`（Harbor、ArgoCD、Jenkins 都有），Alertmanager 发企业微信 / 邮件 | 新增 3 个 Deployment                               | 制造一次 Pod CrashLoop 能收到告警                       |

### P1 CI 与安全（一到两周）



| # | 动作                                                                                                                                                   | 说明                   |
| - | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| 4 | **CI 收敛**：定下 P3 的方案 A，Jenkins 只保留独立任务；两条链路的凭据收敛到同一处（K8s Secret + GitLab CI 变量，各自只读自己需要的）                                                             | 文档里写死 "谁可以写 deploy"  |
| 5 | **镜像扫描门禁**：Harbor 内置 Trivy（`harbor.yml` 开 `trivy`），项目设 "阻止高危镜像拉取"；CI 在 push 后查 `/api/v2.0/projects/.../artifacts/<digest>/additions/vulnerabilities` | 高危数 > 0 即阻断          |
| 6 | **Runner 改造**：shell executor → Kubernetes executor（或至少给 shell 加独立用户 + 工作目录隔离）                                                                        | 这条不做，P3 的 "隔离" 永远是纸面 |
| 7 | **Runner/CI 凭据最小化**：Harbor 用项目 robot（已是）、Artifactory 写权限只在 CI 容器内、GitLab PAT 换成项目级 Deploy Token                                                      | 现有 5 个凭据逐个复核         |
| 8 | **Secret 治理**：Jenkins 已迁 K8s Secret；下一步把 GitLab CI 变量与 K8s 里散落的明文口令统一到 Sealed Secrets 或外部 KMS（本环境可先用 `sops`+age）                                     | 仓库内 `grep` 不到任何口令    |

### P2 稳定与可观测（两到三周）



| #  | 动作                                                                                               | 说明                                       |
| -- | ------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| 9  | **可观测**：Grafana 看板（集群 / CI 成功率 / 构建时长 / 门禁拒绝率 / 镜像拉取失败率）+ Loki 收容器日志                             | 单节点 16G 内可放下（Prometheus 2G 限额、Loki 单机模式） |
| 10 | **资源配额**：所有 ns 设 `ResourceQuota` + `LimitRange`，防一次构建打满整机（现在 `numExecutors: 2` + HPA 4 副本已经接近上限） | `kubectl describe quota` 全程无超卖           |
| 11 | **NetworkPolicy 默认拒绝**：现在只有 podinfo 有，其余平铺；至少给 CI/Jenkins/Sonar/Artifactory 加 "只允许必要出向"          | 断网测试：Jenkins 不能访问 GitLab 以外无关服务          |
| 12 | **PV 治理**：hostPath → local-path StorageClass（或保留 hostPath 但统一到 `/data/pv` 并纳入备份）                 | 节点迁移演练通过                                 |

### P3 高可用（视预算，单节点上收益有限）



| #  | 动作                                | 现实判断                                |
| -- | --------------------------------- | ----------------------------------- |
| 13 | Keycloak 2 副本 + 共享 PG             | **值得做**：它挂了 5 个系统都不能新登录             |
| 14 | Harbor 2 副本（core）+ 共享 registry/db | 值得做，但要先解决 registry 存储（共享 PVC 或对象存储） |
| 15 | Sonar/ArgoCD 多副本                  | 收益中，ArgoCD 多副本较容易（无状态）              |
| 16 | 多节点 + etcd 3 副本                   | **需要第二 / 三台机器**。单节点上做 "假 HA" 只会更脆   |

> 顺序提醒：
>
> **P0/P1 没做完就上 P3，是最常见的 "生产化失败" 路径**
>
> —— 三个单实例副本跑在一台机器上，机器一挂全挂，维护成本却翻倍。

## 5. 如果你只想做三件事

按投入产出比排序，这三件做完，这套平台就从 "演示" 跨到 "能对外说生产"：



1. **备份 + 恢复演练**（半天）：不加任何组件，只加两个 CronJob + 一次真实恢复；

2. **Ingress + TLS + 统一域名**（一天）：解决 "全是 NodePort 明文" 这个最刺眼的问题；

3. **CI 收敛成一条 + 镜像扫描门禁**（两三天）：解决 "两套链路、一个闸门" 的结构性问题。

## 6. 明确不建议做的事



| 不要做                                        | 原因                                              |
| ------------------------------------------ | ----------------------------------------------- |
| 在单节点上给 Sonar/Harbor/Keycloak 各起 2 副本求 "HA" | 同宿主机故障域，机器挂全挂；维护复杂度却翻倍。真要 HA 先加机器               |
| 继续给 Artifactory OSS 找 "专用账号 / 权限目标"        | 已实测 400 `Pro only`，非 admin 只读 200 写 403，属于平台硬限制 |
| 两套 CI 长期并存、各养一套凭据                          | 审计断点、门禁口径不一致，是当前最大的隐性成本                         |
| 为了 "云原生" 上 Service Mesh / 多集群联邦            | 单节点 16G，Istio 控制面就吃掉几个 G，收益为零                   |
| 把 NodePort 直接套 TLS 当 "入口层"                 | 每个端口各自证书、无统一鉴权 / 限流，等于没做入口                      |
| 在 16G 机器上再堆 ES 类组件（如再加一套 ELK）              | 与 Sonar 的 ES、PG 争内存；日志用 Loki 单机模式即可             |
