# 统一访问层方案：MetalLB + TLS + nginx 网关 + 统一域名

> 适用环境：单节点 K8s `192.168.200.12`（kubeadm v1.32、Calico、containerd）
> 落地日期：2026-11-27　　状态：**已上线并通过实测**
> 一句话：把原来 10 个 NodePort 明文入口，收敛成 **1 个 VIP + 1 张证书 + 10 个 `*.corp.local` 域名**。

---

## 1. 为什么这么做（问题 → 决策）

### 1.1 现状的三个硬伤

| 现状 | 后果 |
| --- | --- |
| 每个服务一个 NodePort（30088/30090/30091/30092/30087…） | 端口号满天飞，防火墙要开一堆洞，新人靠背表格 |
| 全 HTTP，没有传输加密 | CI 令牌、LDAP 口令、Harbor token 在网络里明文跑 |
| 无统一入口 | 没有统一的 access log、没有统一的限流/限代、后续加 WAF 无处落 |

### 1.2 三个关键决策 + 为什么

**决策一：用 MetalLB 给入口固定一个 VIP `192.168.200.210`，而不是继续用 NodePort。**

- 单节点上 MetalLB 用 **L2 模式**（ARP 宣告），不需要 BGP、不需要交换机配合，落地成本最低；
- 好处是入口有了一个"像真实负载均衡 VIP"的稳定地址：以后加第二个网关副本、做 DNS 轮询、做防火墙白名单，都围绕一个 IP 走；
- 池子 `192.168.200.200-215` 一次划好，后面 Prometheus/ArgoCD 需要对外暴露时直接给 VIP，不用再改入口。

**决策二：用 nginx 边缘网关（ConfigMap 驱动），而不是 Gateway API / ingress-nginx / NGF。**

这是本方案里最需要解释的一条：

| 方案 | 在单节点上的实际代价 | 结论 |
| --- | --- | --- |
| Gateway API + NGF | 要装 5 个 CRD + 控制面 + 数据面两套镜像，还要调 `nginx.conf` 参数才能避免 413/超时 | 收益（声明式路由）与成本不匹配，**放弃** |
| ingress-nginx | 走 Ingress 资源，但宿主机 GitLab（80 端口）与 phpLDAPadmin（容器 8090）不是集群内 Service，仍要额外造 Endpoints | 多一层抽象，没解决宿主后端问题 |
| **裸 nginx + ConfigMap** | 一个 ConfigMap 装全量 `nginx.conf`，路由规则所见即所得；宿主后端直接写 IP | **采用** |

代价也明确：**改配置必须 `rollout restart`**（`nginx.conf` 走 subPath 挂载，ConfigMap 热更新不会重载）。这一点写进 runbook，避免"改了不生效"的误判。

补充一个**必须做**的写法：后端地址不放在静态 `upstream` 块里，而是放在 `set $backend <地址>:<端口>` 变量里。原因是静态 upstream 会在**启动时**解析 DNS，任一后端不存在 nginx 直接 `[emerg]` 退出并 CrashLoop —— 部署顺序一变就会炸（实际踩过一次，见 5.6）。

而"用 `resolver` + 域名"在本环境**也不好使**：nginx 通过 resolver 拿到的是 `198.18.0.x` 这类伪地址（主机侧透明代理干扰 DNS），一半站点 502。**最终方案是变量里写 Service 的 ClusterIP**：既不做启动期解析，也不依赖 DNS。代价是 Service 重建后 ClusterIP 会变，用 `scripts/gateway/432-check-backend-ips.sh` 定期对比配置与实际（10 个后端一键核对）。

**决策三：自建内部 CA + 通配符证书，而不是每站点自签。**

- 一个 `CORP Internal CA`（10 年）+ 一张 `*.corp.local` 叶子证书（825 天，SAN 覆盖 10 个域名 + `*.corp.local` + IP `.210/.12`）；
- 客户端只需导入 **一次** CA，10 个站点全部受信，`openssl verify` 返回 `0 (ok)`；
- 到期前统一重签一张，不动任何服务配置。

## 2. 目标架构

```
                    ┌─────────────────────────────┐
  办公网 / 笔记本 ──►│ 192.168.200.210  (MetalLB VIP)│
                    └──────────────┬──────────────┘
                                   │ 80 → 301 https
                                   │ 443 (TLS: *.corp.local)
                    ┌──────────────▼──────────────┐
                    │  ns gateway: Deployment      │
                    │  gateway (nginx 1.27, 2 副本)│
                    │  ConfigMap 驱动 nginx.conf   │
                    └──┬───────┬───────┬───────┬───┘
       ┌───────────────┘       │       │       └───────────────┐
       ▼                       ▼       ▼                       ▼
 集群内 Service (ClusterIP)                       宿主机进程（直连 IP）
 gitlab?  jenkins  harbor  sonar                  gitlab  :80   (omnibus)
 artifactory  argocd  keycloak                    ldapadmin :8090 (podman)
 podinfo  webapp  prometheus  alertmanager
```

两条规则：

1. **集群内后端一律写 Service 的 ClusterIP:端口**（变量 `$backend`，见 5.6；不用域名，避免启动期解析与 DNS 劫持）；
2. **宿主机后端一律直连 `192.168.200.12:<port>`**（原因见 5.1 的踩坑记录，别再用"无 selector Service + 手工 Endpoints"接宿主）。

## 4. 部署步骤（从零复现）

> 命令都在服务器上执行；`$` 开头为注释说明，不是命令。

### 4.1 MetalLB

```bash
# 1) 拉镜像并转存到本地 Harbor（library 项目是 public，节点可匿名拉）
podman pull quay.io/metallb/controller:v0.14.9
podman tag  quay.io/metallb/controller:v0.14.9 192.168.200.12:30090/library/metallb-controller:v0.14.9
podman push --creds admin:${HARBOR_ADMIN_PASS} --tls-verify=false 192.168.200.12:30090/library/metallb-controller:v0.14.9
# speaker 同理

# 2) 清单里替换镜像地址后 apply
sed -i 's#quay.io/metallb/controller:v0.14.9#192.168.200.12:30090/library/metallb-controller:v0.14.9#' /root/metallb-native-harbor.yaml
kubectl apply -f /root/metallb-native-harbor.yaml

# 3) 必须等 webhook 就绪，再建地址池（顺序错了会 webhook connection refused）
kubectl -n metallb-system rollout status deploy/controller
kubectl -n metallb-system rollout status ds/speaker

# 4) 地址池 + L2 宣告
cat <<'EOF' | kubectl apply -f -
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata: {name: corp-pool, namespace: metallb-system}
spec: {addresses: ["192.168.200.200-192.168.200.215"], autoAssign: true}
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata: {name: corp-l2, namespace: metallb-system}
spec: {ipAddressPools: [corp-pool]}
EOF
```

### 4.2 TLS（内部 CA + 通配符叶子）

```bash
mkdir -p /root/gateway-tls && cd /root/gateway-tls
# CA
openssl req -x509 -newkey rsa:4096 -sha256 -days 3650 -nodes \
  -keyout ca.key -out ca.crt -subj "/CN=CORP Internal CA/O=CORP Platform"
# 叶子（SAN 用 san.cnf 声明，见下）
openssl req -newkey rsa:2048 -nodes -keyout gateway.key -out gateway.csr -config leaf.cnf
openssl x509 -req -in gateway.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 825 -sha256 -extfile san.cnf -out gateway.crt
openssl verify -CAfile ca.crt gateway.crt        # 期望: gateway.crt: OK

kubectl -n gateway create secret tls gateway-tls --cert=gateway.crt --key=gateway.key \
  --dry-run=client -o yaml | kubectl apply -f -
```

`san.cnf` 关键段（10 个域名 + 通配符 + 两个 IP 一次覆盖）：

```ini
[alt]
subjectAltName = @alt_names
[alt_names]
DNS.1 = corp.local
DNS.2 = *.corp.local
DNS.3 = gitlab.corp.local
...（其余站点同理）
IP.1 = 192.168.200.210
IP.2 = 192.168.200.12
```

### 4.3 网关

```bash
kubectl apply -f /root/gw-manifests/20-nginx-config.yaml
kubectl apply -f /root/gw-manifests/30-deployment-service.yaml
kubectl -n gateway rollout status deploy/gateway
kubectl -n gateway get svc gateway -o wide      # EXTERNAL-IP 应为 192.168.200.210
```

## 5. 踩坑记录（这些别再试）

### 5.1 宿主后端用"无 selector Service + 手工 Endpoints"只有 80 能通

- 现象：`gitlab-host`（→ 宿主 80）正常；`ldapadmin-host`（→ 宿主 8090）稳定 **502**，网关日志 `connect() failed (111: Connection refused)`；
- 但同一时刻，从网关 Pod 里 `curl http://192.168.200.12:8090/` 是 **200**，`ss -ltn` 看不到 8090（podman 端口转发进程），宿主自己 `curl 127.0.0.1:8090` 也是 200；
- 结论：Pod → ClusterIP → DNAT 到宿主同端口这条路径对这个映射不成立，**直连宿主 IP 才是可靠解**；
- 落地：`upstream ldapadmin_host { server 192.168.200.12:8090; }`，改完立即 200。

### 5.2 ConfigMap 改 `nginx.conf` 不会自动生效

`nginx.conf` 是 subPath 挂载，`kubectl apply` 只改 ConfigMap 内容，容器内文件不会更新。必须：

```bash
kubectl -n gateway rollout restart deploy/gateway
```

### 5.3 `worker_connections 2048` 超过默认 fd 上限

启动日志会告警 `2048 worker_connections exceed open file resource limit: 1024`。已在 `nginx.conf` 加：

```nginx
worker_rlimit_nofile 4096;
events { worker_connections 4096; }
```

### 5.4 别在 MetalLB 清单 apply 后立刻建地址池

controller 的 validating webhook 尚未就绪，会报 `failed calling webhook … connect: connection refused`。先 `rollout status`，再建池。

### 5.5 镜像来源限制
`registry.k8s.io` 直连与多数镜像加速站在本环境不可达；`docker.m.daocloud.io/library/*` 可用。转存姿势固定为：`podman pull` → `podman tag` 成 `192.168.200.12:30090/library/<name>:<tag>` → `podman push --creds admin:${HARBOR_ADMIN_PASS} --tls-verify=false`。

### 5.6 静态 upstream / resolver 域名都会让网关崩或 502

- 现象一：加上 `prometheus.corp.local` 路由后，两个网副本各重启 5 次，`--previous` 日志：

  ```
  [emerg] host not found in upstream "prometheus.monitoring.svc.cluster.local:9090"
  ```

  原因：`upstream { server <域名>:<端口> }` 是**启动期解析**，此时 `monitoring` ns 还不存在。

- 现象二：改成 `resolver 10.96.0.10` + `set $backend <域名>` 后，nginx 起来了，但 `jenkins / argocd / podinfo / alertmanager` 变 **502**，error.log 里上游地址是：

  ```
  upstream: "http://198.18.0.34:80/"
  ```

  `198.18.0.0/15` 是主机侧透明代理的伪地址段 —— 说明 nginx 的 DNS 查询被代理劫持，拿到的不是 ClusterIP（同一时刻 Pod 内 `nslookup` 返回的却是正确 `10.96.84.76`）。

- **最终解法**：`set $backend <ClusterIP>:<端口>`，配置里不出现任何域名。既不启动期解析，也不查 DNS。10 个后端 IP 从 `kubectl get svc -A` 取，写在注释里标明对应 Service。
- 配套：`scripts/gateway/432-check-backend-ips.sh` 对比配置内 IP 与实际 ClusterIP，Service 重建后跑一次即可发现漂移。
- 验收：`nginx -t` 通过、新 Pod 重启计数 0、13 域名全通、error.log 无 `502/prematurely`。

> 判断口径：网关"起不来"看 `--previous` 找 `host not found in upstream`；"起来了但部分 502"看 error.log 里的上游 IP 是否落在 `198.18.x.x`。

### 5.7 VIP 从同网段访问不通：节点带着 kubeadm 的"排除外部负载均衡"标签

这是最容易误判为"MetalLB 坏了 / VMware NAT 不转发 ARP"的坑，实际原因只有一行 label。

- 现象：节点自己 `curl https://192.168.200.210/` 正常（走 kube-proxy 的 OUTPUT/KUBE-SERVICES DNAT），但**同网段任何真实主机都访问不到 VIP**；客户端 `arp -a` 没有 `.210` 条目，`ping` 100% 超时；`IPAddressPool`、`L2Advertisement`、Service 的 `EXTERNAL-IP` 全部正确。
- 节点侧取证（注意两个陷阱）：
  1. `arping` **不能在同一台节点上自测** —— `arping -I ens160 192.168.200.12`（节点自己的 IP）同样是 `Received 0 responses`，所以"0 应答"本身不能作为 VIP 故障证据，必须从另一台主机测；
  2. `speaker` 日志在 `info` 级别下看不到宣告决策，只会看到 `createARPResponder interface=ens160`，看起来"已就绪"，实际并未宣告。
- **真正定位手段**：把 speaker 临时提到 debug，读 `should announce l2` 决策行：

  ```bash
  kubectl -n metallb-system patch ds speaker --type=json \
    -p='[{"op":"replace","path":"/spec/template/spec/containers/0/args","value":["--port=7472","--log-level=debug"]}]'
  kubectl -n metallb-system logs ds/speaker | grep 'should announce l2'
  # event=skipping should announce l2 ... reason=speaker's node has labeled
  # 'node.kubernetes.io/exclude-from-external-load-balancers'
  ```

  同时 `kubectl get servicel2status -A` 为空 —— 这个 CR 是 speaker"认领 VIP 到本节点"的记录，**空 = 没宣告**，是比任何日志都快的判断口径。
- 根因：`kubeadm init` 会给 control-plane 节点打上 `node.kubernetes.io/exclude-from-external-load-balancers`，MetalLB 据此把该节点排除在 L2 宣告之外。单节点集群里这就等于**永不宣告**。
- 关键结论：给 `L2Advertisement` 加 `nodeSelectors`（精确匹配本节点）**并不能解除**这个排除（实测仍报同一条 `skipping`），排除标签优先级更高。
- 修复（一条命令，已验证生效）：

  ```bash
  kubectl label node pxe-boot-test-1 node.kubernetes.io/exclude-from-external-load-balancers-
  kubectl get servicel2status -A   # 应出现 l2-xxxxx  ALLOCATED NODE = pxe-boot-test-1
  ```

- 修复后从同网段 Windows 实测：`arp -a` 有 `.210 → 00-0c-29-33-67-86`（即节点 ens160 的 MAC，L2 宣告的正确形态），`Test-NetConnection 192.168.200.210 -Port 443` = True，13 域名全部返回预期状态码。
- **`ping VIP` 仍然不通是正常现象**：MetalLB 的 L2 模式只在 kube-proxy 的 DNAT 规则上接管 TCP/UDP，节点并不"拥有"这个 IP，ICMP 由节点回 `Destination host unreachable`。验收只能用 TCP 端口或 HTTP 状态码，不能用 ping。

### 5.9 切 base URL 这一轮的坑（照这个顺序做就不会翻车）

1. **`kubectl cp` 不认 `deploy/xxx`，只认 Pod**。写 `kubectl -n jenkins cp ca.crt deploy/jenkins:/tmp/` 会报 `pods "jenkins" not found`，后面 `keytool` 就白跑。要么先 `kubectl get pod -o name` 取真实 Pod 名，要么用一次性 `kubectl run` 的临时 Pod 来做（推荐后者，重启不收影响）。
2. **ConfigMap 文件不能 subPath 挂进另一个 ConfigMap 挂载目录**。CoreDNS 原本 `/etc/coredns` 是整目录 ConfigMap 挂载，再往里 subPath 挂 `corp.hosts` 会 runc 报 `... flags=MS_RDONLY|MS_BIND|MS_REC: not a directory`，Pod 直接起不来（`createARPResponder` 级别的报错都看不到，只有 kubelet 事件）。正确姿势：**挂到新目录** `/etc/coredns-extra`（整目录，不带 subPath），Corefile 里写 `/etc/coredns-extra/corp.hosts`。
3. **环境变量同名不要留两条**。给 Keycloak `patch env/-` 追加 `KC_HOSTNAME` 后，旧的 `http://192.168.200.12:30087` 还在列表里。实际生效的是**后一条**（issuer 确实变 https 了），但 spec 里两条同名 env 是埋雷，事后用 python 重排 env 只留一条。
4. **Java 服务要显式灌 CA**。GitLab 用 `trusted-certs`（Ruby 走系统 CA）、Harbor 用 `oidc_verify_cert=false`、dex 用 `insecureSkipVerify: true`、Jenkins 的 `disableSslVerification` 原本就开。**Sonar 的 OIDC 插件没有 skip-verify 选项**，只能改 JVM 信任库：把镜像自带 `$JAVA_HOME/lib/security/cacerts` 复制出来 + `keytool -importcert` 追加内部 CA，存成 Secret，再 subPath 覆盖回原路径（不要新造仅含 CA 的 truststore，会丢掉公共 CA）。
5. **`gitlab-ctl reconfigure` 期间站点 502 是正常瞬态**。reconfigure 会重启 puma/workhorse/nginx，网关侧那 1~2 分钟就是 502，别去查网关配置。
6. **Runner 不是 Pod，是宿主 systemd**。GitLab 切 https 后 CI 克隆地址变成 `https://gitlab.corp.local/...`，靠的是宿主 `/etc/hosts` + `update-ca-trust`，不是集群内 DNS/CA。验证方法：宿主上 `git clone https://oauth2:<PAT>@gitlab.corp.local/root/podinfo.git`。
7. **Pod → VIP 的连通性可以直接测**，不必绕：`python:3.11-alpine` 里 `socket.connect((192.168.200.210,443))` 立即成功，说明 hairpin 没问题；之前网关 Pod 里 `curl` 拿到 000/超时是**应用层**（当时后端正好在重启）。真要看 TLS 层就自己 wrap_socket 打一行 `GET /`，别只信 curl 的退出码。
8. **Harbor 的 `EXT_ENDPOINT` 早晚要改 https，但必须连带处理镜像拉/推**。第一轮改成 https 后发现 `podman login`、Jib 推送、kubelet 按 IP 拉镜像全部报 `http: server gave HTTP response to HTTPS client` / `no basic auth credentials`（实测 pipeline #30 挂），于是回滚成 http 保 CI；但回滚后 Harbor 的 OIDC 回调也跟着变回 `http://192.168.200.12:30090/c/oidc/callback`，Keycloak 直接回 `Invalid parameter: redirect_uri`。**最终解法（本轮落地）**：`EXT_ENDPOINT=https://harbor.corp.local`，同时改三处——containerd 给 `192.168.200.12:30090` 建 `hosts.toml` 别名指向 https 域名（老清单不用动）、GitLab CI 的 `HARBOR_REGISTRY` 变量与 `ci/verify-image.sh` 改域名+https、Jenkins 共享库/Jib 改域名（JVM cacerts 里必须有内部 CA）。根因是 registry 401 返回的 token realm 会跟着 `EXT_ENDPOINT` 走，它不是"对内口径"，改不得又不改不行。
9. **git clone 的 URL 里别带 `#`**。凭据含 `#` 会把它当 fragment 截断（`Could not resolve host: bhR2`），验证克隆要用 PAT 形式 `https://oauth2:<PAT>@gitlab.corp.local/...`。
10. **Windows `hosts` 一行最多挂 ~9 个域名**。一行写 12 个看似正常，实测后 3 个（webapp/prometheus/alertmanager）解析不到（`Resolve-DnsName` 为空、curl 000）。改成**一行一条** + `ipconfig /flushdns` 立即恢复。
11. **Keycloak 报 `Invalid parameter: redirect_uri` 时，先比对"实发 vs 注册"，别猜**。一条命令就能看出来：`curl -D - -o /dev/null -k https://harbor.corp.local/c/oidc/login | grep -i location`，把里面的 `redirect_uri` 解码后跟 `kcadm get clients -r corp -q clientId=<id> --fields redirectUris` 对照。
12. **ArgoCD 真正用的 client 是 `argocd-dex`，不是 `argocd`**。改 `argocd` 的回调完全没效果（登录链路是 `/api/dex/auth/keycloak?...&redirect_uri=.../api/dex/callback`）。同理，新增系统时"Keycloak 里有哪些 client"要全量列一遍，别只改名字对得上的那个。
13. **容器内 curl ≠ JVM 的信任链**。Jenkins 容器里 `curl https://harbor.corp.local` 返回 60（系统 CA store 没内部 CA），但 Jib 走 JVM cacerts 就能通。给共享库的 manifest 校验 curl 加 `-k`，别为了 curl 去改镜像的系统 CA。
14. **触发 Jenkins 构建要"同一会话的 cookie + crumb"**。只 `-u 用户:密码` 取 crumb、不带 cookie jar 去 POST，会稳定 403；正确写法：`curl -s -c /tmp/ck -u user "$J/crumbIssuer/api/json"` 取 crumb，再 `curl -b /tmp/ck -u user -H "Jenkins-Crumb: $C" -X POST "$J/job/<name>/build"`（返回 201）。

## 7. 客户端接入（每人做一次）

Windows（管理员 PowerShell）：

```powershell
# 1) 域名解析（无 DNS 时的临时办法；有内网 DNS 就加 A 记录更优）
#    ⚠️ 一行挂十几个域名在 Windows 上会失效（当时 12 条，实测前 9 个能解析、后 3 个不行）：实测前 9 个能解析、后 3 个（webapp/prometheus/alertmanager）
#    直接解析不到（curl 000、Resolve-DnsName 为空）。必须「一行一个域名」。
'gitlab','jenkins','harbor','sonar','artifactory','argocd','keycloak','ldapadmin','podinfo','webapp','prometheus','alertmanager' |
  ForEach-Object { Add-Content C:\Windows\System32\drivers\etc\hosts "192.168.200.210 $_.corp.local" }
ipconfig /flushdns

# 2) 导入内部 CA（浏览器不再报证书错误）
Import-Certificate -FilePath .\ca.crt -CertStoreLocation Cert:\LocalMachine\Root
```

> Windows 上命令行验证要加 `--ssl-no-revoke`：内部 CA 没有 CRL/OCSP 分发点，schannel 会硬失败报
> `CRYPT_E_NO_REVOCATION_CHECK (0x80092012)`（`curl` 退出码 35）。浏览器对私有 CA 是软失败，不受影响。
> 即：`curl.exe -s --ssl-no-revoke -o NUL -w "%{http_code}" https://gitlab.corp.local/` → 302。

> 校验口径：`foreach ($h in 'harbor','sonar',...) { curl.exe -k -s -o NUL -w "$h %{http_code}`n" https://$h.corp.local/ }`
> 期望：7 个 200（harbor/sonar/artifactory/argocd/ldapadmin/podinfo/webapp）、gitlab/keycloak 302、jenkins 403、prometheus/alertmanager 401。
